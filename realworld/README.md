# Layer C — live-cluster fault-injection campaign

Supports Tables 18–21, Fig. 7 and Sect. 6.13 of the article.

## Re-running the analysis only (seconds, no cluster needed)

```bash
cd orchestrator
python analyse_v1r.py
```

Reproduces all seven computed tables of `results/v1r_analysis.json` exactly from
the released records. The extra `honesty_checks` key in the released file is
regenerated by `../verification/recompute_honesty_checks.py`.

> **Note.** `analyse_v1r.py` and `figures/regen_figs.py` both **overwrite**
> `realworld/results/v1r_analysis.json`, and the file they write does not contain
> the `honesty_checks` key that the released copy carries (those quantities are
> computed by `verification/recompute_honesty_checks.py`, not by the analysis
> script). Restore the released copy with
> `git checkout -- realworld/results/v1r_analysis.json`, or work on a copy of the
> repository.

```bash
cd orchestrator
python analyse_v1a.py     # instrument-validation pilot: 12/12 non-zero edges, 10 of 14 incidents
```

## Repeating the campaign from scratch (about 5 hours, needs a cluster)

Requires Docker, `kind`, `kubectl` and Python 3.10+. Exact versions used are in
`results/provenance_raw.txt` (Kubernetes v1.36.1, `kindest/node:v1.36.1`,
single node, 16 CPU / 7.42 GiB).

```bash
kind create cluster --config kind-cluster.yaml
kubectl apply -f manifests/online-boutique-v0.10.6.yaml
docker build -t im-prober:v1a prober/ && kind load docker-image im-prober:v1a
kubectl apply -f prober/prober-v1a-pod.yaml

python orchestrator/run_v1r.py      # 96 injections: 6 stability, 60 corpus, 30 held-out
python orchestrator/analyse_v1r.py
```

`orchestrator/guard.sh` is the duplicate-launch guard used during the campaign.
`run_v0.py`, `run_v1.py` and `run_v1a.py` are the earlier pilots, kept because the
article cites their outcomes (the 1 Hz pilot that measured zero arrival offsets;
the stability-criterion correction; the cell-admission decisions).

**Results will not match ours exactly.** Real timings depend on the machine, and
the campaign is a physical measurement, not a deterministic simulation. The
released records are the evidence for the numbers in the article.

## Records

| File | Contents |
|---|---|
| `results/v1r_incidents.jsonl` | One JSON record per injected incident: fault, origin, action, timings, onsets, propagation edges, affected set, censoring flag |
| `results/v1r_events.jsonl.gz` | The raw probe stream, 1,711,704 events (823,717 within incident windows) |
| `results/v1r_protocol.json` | Frozen protocol: estimator commit, benchmark digests, censoring window, seeds |
| `results/v1r_allocation.json` | Pre-registered allocation of incidents to cells |
| `results/v1r_analysis.json` | Computed Tables 18–21 |
| `results/v1r_stability.json` | Infrastructure-health gate for the campaign |
| `results/v1_grid_decision.json` | Which (fault, service) cells were admitted and why five were rejected |
| `results/v1a_assessment.json` | Instrument validation of the tiered prober |
| `results/v0_*`, `results/v1_*` | The earlier pilots |
| `results/provenance_raw.txt` | Image digests, Kubernetes and tool versions |

The raw event streams of the `v0`, `v1` and `v1a` pilots are not included here to
keep the repository small; they are available in the archived release.

## Data notes

These are measurements from our own dedicated `kind` cluster. They contain probe
timestamps, benchmark service names, success flags, latencies and gRPC/HTTP
status strings — no personal data, no IP addresses, no credentials.
